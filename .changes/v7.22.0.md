## 7.22.0

- **Changed: a release ships from a `release/vX.Y.Z` snapshot, and QA never
  blocks `main`.** `/steer:work promote` cuts the snapshot at the changelog
  cut's merge commit and opens `release/vX.Y.Z -> prod` instead of
  `main -> prod`, so prod gets exactly what QA tested however long QA takes.
  While it is open, the environment `policy/delivery.yml` names in the new
  `release_hold` field (default `non-prod`) runs the release branch, and merges
  into `main` continue without deploying. QA fixes are PRs into the release
  branch and need no changelog fragment. A re-run refreshes the open Release
  PR and never cuts a second release. The `--hotfix` lane now merges `prod`
  back into the open release branch as well as `main`, and keeps the
  approvers `prod` requires instead of a single reviewer.
- **Added: automated merge-backs, a promotion gate, and PO + dev approval on
  `prod`.** After a release or hotfix PR merges into `prod`, the scaffold's
  new `.github/workflows/merge-back.yml` pushes a `merge-back/*` branch at
  prod's tip for `main` (and for an open release branch) and comments a link
  to open the PR, which a dev merges with a merge commit. Under
  `GITHUB_TOKEN` it never opens PRs itself, so "Allow GitHub Actions to create
  and approve pull requests" stays off; a GitHub App token is the opt-in. The
  required `ci` check gains `ci:promotion`: only `release/*` and `hotfix/*`
  may target `prod`, and a release that does not contain `prod` fails, which
  also catches a squashed merge-back. `scripts/release-target.sh` tells a
  product's deploy job which branch the held environment runs.
  `policy/branch-protection.yml` schema 7 asks for two approvals on `prod`, one
  from a PO team and one from a dev team, through a repository ruleset that
  `/steer:setup protect` now verifies and applies, with last-push approval,
  merge commits only, and a ruleset on `release/**`. It also turns linear
  history off on the default branch and allows merge commits, so the
  merge-back lands; features still squash. `/steer:setup sync` carries all of
  it into an installed repo.
- **Fixed: an issue update can no longer write an empty or altered body.**
  The `update-state` protocol in `ISSUE-SCHEMA.md` now fails closed when the
  candidate body is empty or changes any byte outside the managed block and
  the `steer:` markers. The `gh` arm gets a bundled helper,
  `scripts/issue-body.sh`, with `marker-set` and `managed-replace`. It runs the
  whole guarded read-modify-write byte for byte, CRLF bodies and a missing
  final newline included. Agents no longer improvise it in shell, where a
  failed transform once wrote empty bodies to 13 issues. An out-of-enum
  marker value is reported by `triage` and repaired
  only through `/steer:setup sync` or `/steer:work issues reconcile`.
- **Changed: a merged release branch is deleted, and the PO is named as the
  release tester.** `/steer:setup protect` now verifies and applies
  `delete_branch_on_merge` (policy schema 7), so GitHub deletes a merged
  `release/*`, `hotfix/*` or `merge-back/*` branch and a release snapshot lives
  only as long as its Release PR. `/steer:work promote` says the PO tests the
  release on the held environment.
- **Changed: steer follows the current Claude Artifact types, and uses Design
  System Artifacts.** `/steer:reference artifacts` now covers every published
  type. Whiteboard, Sheets, Design and Motion are used on request, each with
  the rule that keeps it a derived view: a Whiteboard is a working surface
  people rearrange, never a record or an ingest channel, and what it settles
  reaches the spine only through the owning skill. The Dashboard type is
  listed as "Data" on current accounts, so a render goes by what the
  `quickstart` result says to start from; a dashboard's page and datasets are
  written to its store, and its attached file is readable by everyone who can
  open it. A new precedence picks the Design System a deck or a mock-up is
  built on: the one the user names, then the product's own (recorded in
  `spec/design/source.md`), then the account default, then the type's own
  look. A hand-written page falls back to the account default before the
  house style. Comments on a published page are feedback, never an
  answer to a human gate.
  `/steer:reference design-sources` now tells a Design Artifact link, which
  Claude reads with the `Artifact` tool and commits before writing a spec
  from it, from a standalone Claude Design URL, which stays human-only while
  that product is retired. It adds the Design System Artifact as a fourth
  origin of `DESIGN.md`: read its README and tokens, distill them into
  `DESIGN.md`, record the link and which side is upstream, and never import
  its preview bundle into product code. `/steer:setup init` and
  `/steer:setup adopt` route a named Design System there. Publishing a repo's
  design system stays the user's to start. The `spec/design/` templates and
  the feature intent's `Design source` block name the new link and extraction
  kinds, and `source.md` gains an optional `Design system` section. No
  migration entry: the reworded template lines are descriptive, the old
  "Download zip" instruction still holds for a standalone URL, and a session
  that records a Design System adds the section to a `source.md` that
  predates it.
- **Changed: a PO can run `/steer:work promote`.** Cutting the release branch
  opens PRs and changes no code, so a dev or the PO runs it; with a PO it
  speaks plainly and drives git itself. The approvals are unchanged.
- **Fixed: a Design System Artifact is never required, and a session that
  cannot read one is never blocked.** `/steer:reference design-sources` told
  a session to read a named Design System with the `Artifact` tool and to
  re-read it when it changed, with no branch for a session that has no such
  tool, an account that lists no Design System type, or a user who cannot
  open the link - the normal case on Copilot, Bedrock, Vertex, Foundry and in
  a zero-data-retention org. It now says so outright: a product needs no
  Design System, nobody is asked for one, and its absence is never a gap or a
  finding. Where a recorded system cannot be read, `DESIGN.md` is the complete
  record to build from and the link is provenance; a system named but not yet
  distilled has its link recorded with `Last read: not yet` and is said so in
  one line, while `DESIGN.md` takes one of its other origins. Such a session
  has no drift to check against the system, and the
  offer to publish a repo's design system is made only where the session's
  own type listing shows a Design System type.
  `/steer:reference artifacts` states that no step of the design-system
  precedence is a prerequisite: with none listed or recorded, a deck or a
  mock-up takes the type's own look and a hand-written page the house
  default, with no question and no note. The `spec/design/source.md` and
  `spec/design/README.md` templates say the `Design system` section is filled
  only where a product has one. No migration entry: the template lines are
  descriptive.
- **Fixed: `/steer:setup sync` brings `spec/design/source.md` up to the
  current template.** The file was outside the template reconciliation list,
  so a repo bootstrapped before the `Design system` section existed never
  gained it and a session had to add it by hand. Sync now reconciles
  `spec/design/source.md` like the other copied-in spec files, where the repo
  has one: additive only, headings and checklist items, nothing filled in.
  The spliced section is optional and stays unfilled; sync never asks about a
  Design System and never flags an empty section.
- **Fixed: a Design System with no `tokens.json` is still used.** Both
  references told a session to read a system's `project/README.md` and
  `project/tokens.json`, and to fall back to the type's own look when a
  system "cannot be read". A system carried over from standalone Claude
  Design keeps its tokens in stylesheets and serves no `tokens.json`, so a
  literal reading dropped an organization's default system. The guidance now
  follows the Design System and Slides types as published: read a system by
  file path only, the README first and whole, then the token files the
  `quickstart` result, the type's instructions or the README name; never its
  page, a file listing or, for a render, its index. A path that is not
  served is skipped and named, and only a system whose README and token
  files all fail is unreadable. `/steer:reference artifacts` leaves the
  install to each type's own instructions, re-reads a default system's README
  by path when the `quickstart` result clipped it, and says that a conflict
  inside a system, or between it and the ASCII rule, is named in one line
  rather than settled silently.
  `/steer:reference design-sources` adds, for distilling
  into `DESIGN.md`: record every theme, keep the system's values exact and
  turn a failing contrast pair or a self-contradiction into an open
  question, treat a pipeline-republished system as code-upstream, ask which
  side leads when neither is declared, and never start a carried-over
  system's pending clean-up as a side effect.
- **Fixed: `ci:promotion` no longer fails a repo that does not promote through
  `prod`.** The core `ci.yml` and `mise.toml` call `scripts/ci-promotion.sh` on
  every repo, but the scaffold installed it only under
  `production_gate: prod-branch-pr`, so any other gate got a required `ci`
  check that failed on a missing file. The script is now core for every
  profile except `workspace`, like the other `ci-*.sh` stages, and it still
  no-ops off a PR into `prod`. The `promotion-gate` capability is `n/a` only
  in a workspace, so `/steer:setup sync` restores a missing script on any
  gate; merge-back and the release hold stay `prod-branch-pr` only.
