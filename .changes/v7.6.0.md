## 7.6.0

- **Added: `/steer:spec questions needs` lists everything the client still
  owes before a wave of work.** Until now, nothing collected the access
  requests, accounts to provision, and decisions a team needs from the
  client: `questions bundle` saw only spec questions, and access and tooling
  gaps had no category. The new mode reads the spine, `policy/*.yml`, ADRs
  and, through `/steer:tracker-sync`, the wave's issues (`--milestone <m>`
  narrows it), and proposes one `### Q-NNN` question per gap. Each proposal
  names its evidence (a file, a field, an issue). Nothing is written until
  the dev confirms the list. From there the existing path takes over:
  `bundle` renders the questionnaire and `intake clarify` folds the answers.
  Open questions gain an optional `kind:` field (`clarification`,
  `decision`, `access`, `tooling`; absent means `clarification`, so existing
  questions behave as before). `bundle` now groups questions by kind, and it
  always includes an `access`, `tooling` or `decision` question, whatever
  its `owner:`. An `access` question asks the client to grant or confirm
  access, never to send a secret. Every `access` field in the questionnaire
  says not to paste passwords, keys or tokens, and `intake clarify` stops
  before committing a returned document that contains a credential. The
  SessionStart open-questions reminder counts the same audience: an
  `access`, `tooling` or `decision` question counts as the client's to
  answer whatever its `owner:`, so it can tip the nudge toward
  `/steer:spec questions bundle`. The `ci:spec` stage and `/steer:spec
  validate` reject an unknown `kind:` value. A consumer repo picks up the
  updated `scripts/ci-spec.sh` and `scripts/spec-questions.sh` through
  `/steer:setup sync`.
