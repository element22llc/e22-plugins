## 7.27.0

- **Changed: a release is one PR.** `/steer:work promote` no longer opens a
  changelog cut PR into `main` and waits for it to merge. It cuts
  `release/vX.Y.Z` from `main`, commits the changelog cut on that branch, and
  opens the Release PR into `prod` in the same run. The merge-back that
  already follows every release brings the cut to `main`, as it does for a
  hotfix; until it lands, `main` still lists the fragments the release
  consumed and `promote` refuses the next release. A version already cut on
  `main` the old way is snapshotted as before. `promote` also stops on a
  changelog cut PR still open from the old flow, and on a `release/*` branch
  left on origin that `prod` does not contain: one that contains `main` is
  still the release and gets its Release PR opened, any other is a dev's
  call. GitHub refuses a new `release/**` branch whose tip has no green `ci`,
  so `/steer:setup protect` now builds the `steer: release branches` ruleset
  with `do_not_enforce_on_create: true`: `ci` and the pull-request rule still
  bind every later push, and `ci` runs on the Release PR. What the flag
  opens: a writer can create a `release/**` branch at any commit, reviewed
  or not; a workflow that runs on a push to `release/**` runs that commit's
  own copy, and under the release hold the held environment deploys it once
  its Release PR opens. The gate into `prod` is unchanged. **A repo
  protected before this version must re-run `/steer:setup protect` once** -
  `promote` stops at the refused push and says so until then
  (`MIGRATIONS.md`).
