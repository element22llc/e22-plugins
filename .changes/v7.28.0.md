## 7.28.0

- **Added: `/steer:work qa` attaches before/after screenshots to the PR.**
  On a UI diff it now captures each changed screen at desktop and narrow
  width, from the default branch (booted in a throwaway worktree) and from
  the branch, after its fixes are in. A new helper, `scripts/pr-assets.sh`,
  pushes them as orphan commits to one hidden ref per branch,
  `refs/steer-assets/<branch>`, and links them by commit SHA. A hosting spike
  (#1006) showed `github.com` URLs render in a private repo's PR body, while
  repo-relative paths and `raw.githubusercontent.com` links do not.
  The ref is not a branch, a default clone never fetches it, and it never
  enters the default branch's history. It is kept as review evidence, and
  `qa` documents a one-line prune. The consumer PR template gains a
  *Visual changes* section with an N/A box. Solo-trunk has no PR body, so
  it skips the images and says so. `qa` itself stays opt-in.

- **Security: skill grants for bundled helpers are anchored to the plugin root.**
  The 25 `allowed-tools` entries that pre-approve a helper script used the
  shape `Bash(sh *scripts/<name>.sh*)` (and `python3` for
  `scaffold_reconcile.py`). The leading wildcard also matched
  `sh -c '<anything>' x scripts/<name>.sh` and a script with the same name
  anywhere in the repo, so either ran with no prompt. Each entry is now
  `Bash(<interp> "${CLAUDE_PLUGIN_ROOT}/scripts/<name>" *)`. Claude Code
  fills in the plugin path there as it does in the skill body. Grants match
  the command string literally, quotes included, so the helper calls that
  were split across lines or unquoted now sit on one line in the quoted
  form. Claude Code fills in the path only in a `SKILL.md`, so a helper call
  in a file the agent reads later reached Bash with the variable and was
  refused, before and after this change. The eight skills that run such calls
  now tell the agent to write the path in, so those helpers stop prompting
  too. `check_standards.py` rejects an unanchored grant, any other spelling
  of a helper call (including one continued with a backslash), and a skill
  missing that instruction (#1010).

- **Fixed: adding a mise tool to a locked repo no longer breaks CI, and Semgrep
  runs pinned through `uvx`.** The v7.23.0 gitleaks migration and the
  `security-gate` repair added `[tools]` entries with no lock step, and
  `mise install` records a new tool's version but no platform URLs, so CI's
  locked install failed on a multi-platform `mise.lock` (#953). They now lock
  the added tool by name for the platforms the lock already covers, derived
  from the lock itself; `CONVENTIONS.md` -> "Adding a tool to a locked repo"
  states the rule, and sync, adopt and the reference summary point at it. The
  scaffold's `"pipx:semgrep"` tool, which can force a lockfile format upgrade
  that rewrites every entry (#925), is gone: `scripts/ci-security.sh` runs
  `uvx --exclude-newer "${STEER_SEMGREP_EXCLUDE_NEWER}" --from
  "semgrep==${STEER_SEMGREP_VERSION}"`: Semgrep pinned to 1.185.0, and its
  transitive deps bounded to packages published by 2026-11-16, the two set
  together on adjacent lines. Its error messages print the same command for a
  local run. Two migrations carry repos forward: one moves a repo off
  `pipx:semgrep` to the pinned `uvx` call, the other locks a gitleaks or Trivy
  entry that lacks CI's `linux-x64` platform. gitleaks and Trivy stay
  `latest` in `mise.toml`, pinned by `mise.lock`.

- **Fixed: a `/steer:setup sync` PR that edits mise config now says why its
  CI may go red at `Setup mise`.** Editing `mise.toml` or `mise.lock` changes
  the `jdx/mise-action` cache key, so the sync PR is the first run to install
  every tool fresh. mise's npm `trustPolicy=no-downgrade` check can then fail
  an `npm:` tool that cached runs on other PRs were masking, and the red
  reads as the sync breaking CI. The PR body now notes the cache miss, tells
  a pre-existing exposure from one the sync introduced, and names the
  reviewed, narrow remedy: `trust_policy_excludes` for the one version the
  error names, on that one tool, then `mise lock`. Sync never adds the
  exclude itself (#926).

- **Fixed: sync keeps the tags the lock run writes over SHA pins.** The
  v7.23.0 `actions.lock` migration told sync to leave a product workflow's
  `@<sha> # vX.Y.Z` pins alone and only suggest a rewrite, but
  `lock-workflows.sh` rewrites every full-SHA pin to the tag at its commit
  and locks only that tag. A repo that put the SHA pins back passed
  `gh actions-lock --verify`, and the runner refused the workflow at
  startup with no jobs. The entry now has sync commit the refs as the lock
  run leaves them, call each rewrite out in the PR and put back a dropped
  `# zizmor: ignore[...]` comment. The scaffold `MANIFEST.md` and
  `CONVENTIONS.md` say the same. A new migration finds a SHA pin the
  lockfile does not list, in a repo that already ran the old entry, and
  re-runs the lock helper to restore the tag (#923).

- **Changed: `/steer:work` asks its reviewer notes in the session instead
  of leaving a draft for later** (#1017). A medium finding or design question
  the code gate leaves used to keep the PR a draft, with a handoff telling the
  author to read the notes and mark it ready. When the author is in the
  session, `finish` now puts each note to them, one question per note with a
  recommended resolution and `Decide later`. It records each answer under
  the note as decided in-session, applies any change an answer asks for,
  then readies the PR and watches CI. A `queue` worker still never asks: its
  card now lists the notes, and the orchestrator asks them at Step 4 and
  sends the answers back to the worker. `drive` and `review --mine` do the
  same. A PR stays a draft on an unattended run, an open high finding, a
  flagged drift class, or a note answered `Decide later`.
