## 6.4.0

- **A repo can now drive its spec spine with OpenSpec and keep every other
  standard.** steer assumed one spine layout - `spec/features/<id>/intent.md` +
  `contract.md` - so a repo using OpenSpec (Fission-AI) got the worst of both:
  rule 30 told every session to write artifacts in a place the repo does not
  use, and `check-unmanaged-repo.sh` read the missing `spec/` as *unmanaged*
  and served the full greenfield bootstrap card at every session start,
  pushing `/steer:init` - which would have laid a competing spine next to
  `openspec/`. The fix is a scope predicate, not a second plugin: a new
  `has-openspec` token (structural marker required - `openspec/project.md`,
  `openspec/specs/` or `openspec/changes/`, since a bare `openspec/` directory
  proves nothing, exactly as `spine.sh` refuses to read a bare `spec/` as a
  spine) gates a new rule `33-spec-workflow-openspec`, which remaps the spec
  artifacts onto `/opsx:propose` / `apply` / `archive` and states plainly that
  every other rule - stack, testing, coverage, Definition of Done, issue-first,
  drift gates, secrets, compliance, change size - is unchanged. The bootstrap
  notice swaps to a short OpenSpec orientation instead of the greenfield card.
  Rule 30 is deliberately left unmarked rather than paired with a negated
  token - a marked rule is skipped wholesale in knowledge-work mode, where the
  injection banner promises spec-workflow still applies - so rule 33 overrides
  it in prose and both are delivered together. Repos without `openspec/` pay
  nothing: the measured `code` profile is unchanged.

  **ADRs, the tracker declaration and the app guide stay steer's, and live
  under `openspec/steer/`.** OpenSpec models none of them: a change's
  `design.md` is per-change and is archived with it, so it cannot hold a
  decision that must outlive the change; the tracker declaration is what
  issue-first enforcement reads; and the app guide is living documentation
  rather than a spec artifact. Parking them in a thin `spec/` beside
  `openspec/` would leave such a repo with two spine directories and no way to
  tell which was truth, so they sit in one namespaced place instead. The
  `steer/` segment is load-bearing rather than decorative: `openspec/` is
  written by a third-party CLI - `openspec update` regenerates
  `openspec/AGENTS.md` wholesale, and `openspec archive` relocates whole
  change directories - so a flat `openspec/decisions/` would be one upstream
  release away from a collision, while a namespaced subtree that upstream will
  not claim is not. **Native repos are untouched:** `spec/` still resolves
  exactly as before, and the whole feature is inert without an `openspec/`
  marker.

  The path is resolved in **one** place - `steer_tracker_file` /
  `steer_decisions_dir` in `hooks/lib/scope.sh`. Every issue-first hook
  (`check-write-nudges`, `check-bash-actions`, `reconcile-issue-first`) already
  reached the tracker through `steer_tracker_is_github` rather than by naming
  the path, so redirecting that one helper moved all of them; only
  `scan-capabilities.sh` and `workspace-snapshot.sh` needed touching. The
  resolvers **assign** rather than print, because they sit on the PreToolUse
  hot path where a command substitution would fork a subshell on every tool
  call. Skill bodies keep their native `spec/` prose and rule 33 states the
  override, the same pattern that already lets rule 33 override rule 30 - 28
  skills did not have to be edited to move these artifacts.

  **`steer_spine_state` gained two outcomes rather than a second bypass.**
  `openspec` (steer's artifacts present) and `openspec-setup` (an `openspec/`
  spine with steer's side not laid down yet) are tested first, because such a
  repo may have no `spec/` at all - which the old ladder read as `unmanaged`,
  i.e. the full greenfield bootstrap card pushing an init that would lay a
  second, competing spine. Making it a state instead of a special case in
  front of one caller is what keeps `/steer:doctor`, `/steer:sync` and
  `/steer:audit` answering the same question the same way. A `MIGRATIONS.md`
  entry carries across any repo that already holds these artifacts in a thin
  `spec/` beside `openspec/`, and until it runs the session is told so
  explicitly rather than silently reading a different `tracker.md` from the
  one being edited.
- **An OpenSpec repo is no longer pushed at `/steer:init` from the write path,
  and the app guide follows the other steer artifacts.** Moving the ADR log and
  the tracker declaration under `openspec/steer/` left three places still
  reasoning about the native spine, two of which were real defects rather than
  stale wording:

  - **`check-write-nudges.sh` pushed the competing bootstrap at write time.**
    Its spine dimension fires on any state that is not `managed`, so an
    OpenSpec repo - a *complete* spine, just not steer's - was told it had "no
    `/spec` spine" and pointed at `/steer:init` on the first source write. The
    SessionStart notice had already declined to say that; the write-path nudge
    said it anyway, later in the session, where nothing contradicted it.
    `openspec` is now excluded alongside `managed`, `openspec-setup` gets a
    note naming the missing tracker template instead of a bootstrap, and the
    scaffold clause - which still applies, since the toolchain is wanted here
    too - gained a variant that asks for the bundled scaffold directly rather
    than via `init`.
  - **`/steer:sync` would have recreated a stray `spec/`.**
    `scan-capabilities.sh` reported the `app-knowledge-docs` capability from a
    hard-coded `spec/app/README.md`, so on an OpenSpec repo it read `absent` -
    and sync *repairs* an absent capability by creating the file, on the very
    repo that had just moved out of `spec/`. The app guide now resolves through
    `steer_app_docs_dir` to `openspec/steer/app/`, and the migration entry
    moves it with the other two.
  - **The issue-first nudges named a file the repo does not have.** Four
    user-facing strings hard-coded `/spec/tracker.md` while the *gating* read
    the resolved path - so the text taught the wrong location for the file it
    was enforcing. They interpolate `steer_tracker_rel` now.

  `/steer:setup`'s routing table also gained rows for the two OpenSpec states,
  since it had none and could not have routed them anywhere sensible.
- **Typographic characters are now denied at write time, not just discouraged
  in prose.** Rule 85 has always said ASCII belongs in code and values - em
  dashes, curly quotes, ellipsis, arrows and non-breaking spaces are for prose
  and docs - but it was a bullet in an always-on ruleset, and always-on prose
  is exactly what a long session drifts past. The cost was not cosmetic: an
  AWS resource name or `description` carrying an em dash is rejected by the
  API's validator, so the break surfaced at deploy time rather than at the
  keystroke that caused it. A new `PreToolUse` hook,
  `check-ascii-writes.sh`, inspects only the text a `Write` / `Edit` /
  `MultiEdit` / `NotebookEdit` *introduces* and **denies** the write, naming
  each offending character with its codepoint and the ASCII substitute
  (`em dash U+2014 -> -`), so the rewrite is one step instead of a guess. It
  is a deny rather than a notice for the same reason `check-version-pins.sh`
  is: the check is deterministic, a `PostToolUse` notice cannot unwrite the
  file, and a mechanical fixup is unsafe - rewriting a curly quote inside a
  string literal can break its quoting. Copilot CLI gets an `ask` instead, as
  with every other gate there.

  **It is comment-aware, and that is the whole design.** Rule 85 permits these
  characters in prose, and the bundled scaffold depends on that - every
  `mise.toml`, `compose.yaml` and CI script opens with a typographic header
  comment, because the Code comments rule asks for one. So comments are
  stripped before the scan and only value positions are inspected; a header
  comment is never flagged. Every stripping heuristic is biased to over-strip
  (a `//` is only a comment when it does not follow a `:`, so a URL survives),
  because a missed character merely leaves the always-on rule in force while a
  false deny is what gets a gate switched off. Scope is `implementation` and
  `operations` files with a known comment syntax, plus `.hcl`; documentation,
  the `/spec` spine, lockfiles, generated output and unrecognized file types
  are untouched.

  **Non-English copy is deliberately safe.** Only the enumerated rule-85 set
  matches - dashes, curly quotes, ellipsis, bullet, arrows, non-breaking and
  thin spaces. Accented Latin letters, guillemets, CJK and emoji are not in it
  and never trip the gate. A deliberate character (a fixture asserting one, a
  Unicode table) is declared with `steer:allow-typographic` in the same
  content, mirroring `steer:allow-pin`.

  **The bundled templates were carrying the bug they now prevent.** Eighteen
  shipped templates held em dashes in value positions - `mise.toml` task
  `description` strings, `ci-*.sh` notice text, GitHub issue-form labels and
  dropdown options, workflow step names - so `/steer:init` and `/steer:adopt`
  would have written files this very gate then denied. Those are corrected to
  plain hyphens; comment lines are untouched. A fixture case runs the hook's
  own stripper across every non-Markdown template and fails if one regresses,
  so the templates cannot drift back.

  **Known gap:** writes performed through `Bash` heredocs are not inspected,
  the same documented bypass `check-version-pins.sh` carries.

  **Along the way: a broken `jq` no longer silently disables a gate.**
  `steer_have_jq` promised "a usable `jq` on PATH" but only tested presence, so
  a `jq` that is installed yet cannot execute - a half-installed or
  architecture-mismatched build, a shim - took the `jq` branch, returned an
  empty payload, and every hook reading its input through that helper fell
  through to its fail-open exit instead of degrading to the grep fallback
  written for exactly that case. It now probes execution as well, once per
  process and cached, so the fallback stays reachable. This affects
  `check-version-pins.sh` and the write-path nudges as much as the new gate.
- **The bundled scaffold no longer teaches the comment habit rule 08 forbids.**
  Rule `08-code-comments` has said "why-only" since v6.1.0, but the templates
  `/steer:init` and `/steer:adopt` instantiate were themselves comment-heavy -
  `changie.yaml` at 53% comment lines, `scripts/ci-changelog.sh` at 40%,
  `mise.toml` at 32% - so the first thing a managed repo saw was the density
  the rule tells it to avoid, and new code was written to match the file it
  landed in. The essays are gone; what they said is not lost, because nearly
  all of it was already in `templates/reference/CONVENTIONS.md`:

  - **`scripts/ci-changelog.sh`** carried a twenty-line header restating
    CONVENTIONS' "Changelog" section almost verbatim (what counts as shipping,
    what satisfies the gate, base resolution). Cut to the one-line header the
    rest of the scaffold already uses plus the one fact CONVENTIONS does not
    carry - that the gate is deliberately delivery-mode-blind.
  - **`changie.yaml`** lost the fragments/curation rationale and the
    release-cutting walkthrough, both duplicated in CONVENTIONS, and keeps the
    `%-m`-vs-`%m` and same-second slug-collision traps that nothing else
    records.
  - **`mise.toml`** lost a banner-divider block and a nine-line `pre-commit`
    essay, both covered by CONVENTIONS' "Standard mise tasks".
  - **`scripts/ci-lib.sh`** lost a "converge this the next time that gate is
    touched" note - task history, which rule 08 excludes by name.

  Deliberately **not** stripped: the commented-out opt-in stanzas
  (`replacements`, `[monorepo]`, the Ansible provider and `ansible:lint`), which
  `CAPABILITIES.md` and `POLYREPO.md` document as the consumer's to tune; the
  `# vX.Y.Z` SHA-pin comments the actions-security gate requires; and
  `policy/branch-protection.yml`, whose comments each name a non-obvious
  constraint (why `strict: false`, why the `solo` profile exists, why repo-wide
  auto-merge stays off) rather than prose to trim.
- **A freshly bootstrapped repo no longer fails its own required `ci` gate on
  the scripts steer just installed.** `mise run ci:hygiene` shellchecks every
  tracked `*.sh`, and two bundled scaffold scripts were not clean under the
  bare shellcheck a consumer repo runs: `scripts/ci-changelog.sh` sourced
  `ci-lib.sh` with a bare `. "$(dirname "$0")/ci-lib.sh"` and tripped SC1091
  (every sibling `ci-*.sh` already carried the `HERE=` resolution plus the
  `source-path=SCRIPTDIR` / `source=ci-lib.sh` directives), and the workspace
  profile's `scripts/ws.sh` tripped SC2016 ten times on single-quoted `printf`
  strings whose backticks are literal markdown in user-facing output. Both are
  now clean: `ci-changelog.sh` matches its siblings verbatim, and `ws.sh`
  carries a file-level `disable=SC2016` with the reason.
- **The gate that should have caught them now does.** `mise run shell` linted
  the shipped scaffold under this repo's own `.shellcheckrc`, whose SC1091 and
  SC2016 disables are scoped to the plugin's runtime hooks - so it masked
  exactly the findings that break a consumer, which has no `.shellcheckrc` at
  all. `shell` now makes a second `--norc` pass over the shipped scaffold
  scripts only, so a scaffold script that would fail a bootstrapped repo fails
  here first.
- **The comment-density notice now reaches the Copilot CLI, and stops counting
  lint directives as prose.** Two gaps that let comment-heavy writes through:

  - **Copilot CLI parity.** `copilot-hooks.json` carried no `PostToolUse` entry
    at all, so the density notice fired only on Claude Code and on Copilot in
    VS Code (which runs the Claude `hooks.json` directly). The Copilot CLI got
    nothing. `gen_copilot_hooks.py` now ports `check-comment-density.sh` under
    the **PascalCase** `PostToolUse` key, which is load-bearing twice over:
    Copilot applies Claude matcher semantics there, so `Write`/`Edit` resolve
    to its runtime `create`/`edit` tools (the camelCase form would match
    neither), and it feeds the snake_case `tool_name`/`tool_input` payload the
    script already parses. The hook emits a **top-level** `additionalContext`
    on that surface - the CLI documents only the flat key and never mentions
    Claude's nested `hookSpecificOutput`, so the notice would otherwise be
    dropped.
  - **Directives are not comments.** The counter matched any line whose first
    non-space character began a comment, which swept up the shebang and every
    `# shellcheck`, `# noqa`, `# type:`, `// eslint-disable` and
    `// @ts-expect-error` line. Short, directive-dense scripts therefore read
    as comment-bloated - `scripts/ci-deps.sh` scored 38%, above the notice
    threshold, on five lines of prose - which pointed the fix at the genuine
    why-comments sitting beside the directives. Directives and the shebang are
    machine-read instructions the file cannot work without; they still count
    toward the line total, just not as comments.
- **The comment-density notice now blocks above a third, advises above a fifth,
  and can be waived once per file.** A single advisory tier at one-third left
  the common case unaddressed: a file at 25-30% comment lines is far past
  why-only, and nothing said so. And a notice the model may skip is exactly what
  rule `08-code-comments` needed backing *against*.

  - **Two tiers.** 20-33% emits the advisory `additionalContext` as before, once
    per file per session. At or above a third the hook returns a `decision:
    "block"` with the reason. Be clear about what that buys: on `PostToolUse`
    the write has already landed, so `block` places the reason **beside the tool
    result** rather than undoing anything - materially more salient than ambient
    context, but not a gate. The PR review remains the wall.
  - **The block tier re-fires** while the file is still over, capped at three per
    file per session - one dismissable notice is the failure mode this tier
    exists to escape, and the cap stops a file that genuinely cannot be trimmed
    from nagging.
  - **`steer:allow-comments <reason>`** anywhere in the file silences both
    tiers. Deliberately file-level, unlike the per-line `# steer:allow-pin`,
    because density is a property of the whole file; the reason is **required**,
    so the hatch cannot be taken silently. It is not a `pin-ok`-style legacy
    alias and has none.
  - **Copilot CLI keeps parity.** `postToolUse` has no `decision` field there,
    so the block tier prefixes its text with `BLOCKED:` instead of being
    dropped - the surfaces read the same rather than one carrying a safety net
    the other lacks.

  Four shipped scaffold files whose density is deliberate - `changie.yaml`,
  `policy/branch-protection.yml`, and the `infra`/`workspace` profile
  `mise.toml`s, all triaged when the templates were stripped - now carry the
  marker with their reason, so a consumer editing them is not nudged about
  comments that were already judged to earn their place. No shipped scaffold
  file lands in the block tier.
- **The bundled Dependabot auto-merge workflow no longer fails on a repo's
  first Dependabot PR.** `dependabot-auto-merge.yml` declared only
  `contents: write` and `pull-requests: write`, and a Dependabot-triggered run
  gets **exactly** the permissions the workflow declares. Its wait step runs
  `gh pr checks`, which resolves the GraphQL `statusCheckRollup` field - that
  reads check runs (`checks`) and commit statuses (`statuses`), neither of
  which was granted. So the job approved the PR and then died with
  `Resource not accessible by integration
  (node.statusCheckRollup.nodes.0.commit.statusCheckRollup)`: every managed
  repo got a red Actions run on day one and the patch bump never merged. The
  workflow now declares `checks: read` and `statuses: read` alongside the two
  write scopes. `check_standards.py` gained the invariant - any bundled
  workflow whose `run:` reaches for `gh pr checks` must declare both read
  scopes - so the permissions map cannot drift away from the command it runs
  again, and a ledger entry carries the two lines into already-bootstrapped
  repos on the next `/steer:sync` (YAML workflows are reconciled by eye, not
  by the additive helpers). Reported as issue #566.
- **The ASCII gate above now covers prose too, and rule 85 drops its prose
  exemption.** As first shipped, the gate stripped comments and scanned only
  value positions, because rule 85 said typographic characters "belong in prose
  and docs" and the concrete failure was an AWS resource name rejected by its
  validator. That exemption was the real problem: em dashes, curly quotes,
  ellipsis and arrows kept spreading through comments, specs, docs and chat -
  the half that reads as machine-written - and prose is where values get copied
  from in the first place. Rule 85 is now **ASCII everywhere**: not in code,
  config, identifiers or strings bound for an external API, and not in
  comments, specs, docs, commit messages, PR text or chat either. Write `-`,
  `'`, `"`, `...`, `*`, `->`.

  `check-ascii-writes.sh` scans raw. The comment stripper and its
  per-extension comment-style map are **deleted** rather than bypassed: with
  prose in scope they were dead code, and leaving them in would invite the
  exemption back. Scope widens from `implementation` / `operations` to every
  authored text class (`documentation`, `spec`) plus `.hcl`; lockfiles,
  generated output and unrecognized file types stay out, and the plugin's own
  source repo is still exempt at the hook but now covered by its own
  committed-state gate, which reuses the same character table so the two
  cannot drift apart.

  **Nothing fails retroactively in an existing repo.** The gate only sees text
  a write *introduces*, so legacy prose is untouched until someone edits it, at
  which point that line converts; an edit that *removes* one of these
  characters is never denied, and `steer:allow-typographic` in the same content
  remains the escape hatch for a genuine exception. **Non-English copy is
  unaffected** - the matched set is unchanged, so accented letters, guillemets,
  CJK and emoji never trip the gate. The bundled templates and every other
  tracked file in the plugin repo were converted in the same change (14,392
  occurrences across 606 files), and the fixture that sweeps the bundled
  templates now covers Markdown as well.
