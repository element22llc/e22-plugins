## 6.3.0

- **Fixed: `/steer:init` no longer clobbers a repo's own `pre-commit` hook, and a
  legacy template fork now gets a commit gate at all.** 6.2.0 wired the gate from
  both setup skills, but only `/steer:adopt` carried the collision guard -
  `/steer:init`'s step 5 ran `mise generate git-pre-commit --write`
  unconditionally, and the generator does not refuse a collision - it renames the
  existing hook to `pre-commit.old` and takes its place, and it writes into
  `core.hooksPath` when one is set. So a repo that already owned a commit gate
  (husky, a hand-rolled hook) had it displaced by bootstrap, and one pointing
  `core.hooksPath` at a *tracked* directory had that swap land as a versioned
  change on top. Init now applies the same guard as adopt: report the
  collision and leave it alone, because a repo with its own commit gate is a
  decision, not a gap - the same reading `/steer:sync` already gives the
  `commit-gate` capability, where a foreign hook scans `n/a` rather than
  `mis-wired`. Both skills now name the detection command (`git rev-parse
  --git-path hooks`, which honours `core.hooksPath` and resolves a linked worktree
  to the primary checkout) instead of leaving it implied. Init **Path A** (a
  legacy fork of the old `repository-template`) wired no gate at all -
  `LEGACY-TEMPLATE-FORK.md` never mentioned it - so the fork path now wires it
  after the `mise` tasks are adapted, under the same guard; a fork predating the
  bundled scaffold is the repo most likely to carry a commit gate of its own.

- **Added: every managed repo gets an automated, curated `CHANGELOG.md`.** The
  standard already promised one - rule `45-commit-autonomy` says "commit
  messages are not the release changelog - that stays the curated
  `CHANGELOG.md`", `CONVENTIONS.md` says it is "not derived by parsing commit
  types", and the scaffold shipped a `CHANGELOG.md merge=union` driver for it -
  but nothing ever installed the file, so the promise was unkept in every
  consumer repo. The scaffold now carries `.changie.yaml` plus a `.changes/`
  tree, and entries are written as **one YAML fragment per change** under
  `.changes/unreleased/`; `changie merge` assembles `CHANGELOG.md` at release.
  Entries stay hand-written - changie automates assembly and the version bump,
  never the prose - so this *implements* the existing standard rather than
  reversing it to commit-derived generation. One file per change also means
  concurrent PRs never collide, which retires the scaffold's `merge=union` row:
  union is line-based and splices multi-line entries together wrongly, the same
  reason `spec/history/` is a directory. A new `ci:changelog` gate fails a PR
  that changes shipping code without a fragment, `/steer:sync` repairs the
  wiring in already-adopted repos, and `/steer:work` writes the fragment as part
  of finishing a unit of work. `library`/`cli` repos cut with `changie batch
  auto` (semver from each fragment's kind); `app`/`service` repos cut a CalVer
  date at the `prod` promotion.

- **Fixed: the `ci:changelog` task no longer describes itself as PR-scoped.** Its
  `mise` description read "PR-scoped", while rule `50-definition-of-done` calls the
  changelog-fragment gate "delivery-mode-blind and so fires on a trunk push too"
  and the script it runs says the same in its own why-comment - deliberately
  mode-blind, because in solo-trunk there is no PR at all and the gate is the only
  thing standing between a trunk push and an unrecorded shipped change. The code
  always matched the rule (`ci-lib.sh` resolves a base for `STEER_CI_EVENT=push`
  from `STEER_CI_BEFORE`, and the shipped `ci.yml` triggers on `push` to `main`),
  so only the description was wrong - but it was wrong in the direction that
  leaves a solo-trunk repo unprepared for a red trunk push.
