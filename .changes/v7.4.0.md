## 7.4.0

- **Added: steer keeps independent work off PR stacks.** An agent that cut
  each issue branch from the previous one and opened each PR against it
  built a 64-PR chain of unrelated fixes: a stack merges only bottom-up, with
  every layer approved, so none of them could land alone. `/steer:work start`
  now cuts a new branch from the freshly fetched default branch, and stacks
  on another work branch only when the issue needs that PR's unmerged code,
  saying so in the PR. To land many fixes as one merge, rule 45 names the
  sibling pattern instead: open each fix's PR against a `batch/<slug>` branch
  cut from the default branch, review and merge them in any order, then land
  the batch with one PR. A new PreToolUse check asks the human before any
  `gh pr create` or `gh pr edit` whose `--base` is a work branch, and before
  `gh stack submit`; the default branch, `prod`/`staging`/`develop`,
  `release/*`, `batch/*` and the promotion PR stay silent. An unattended loop
  cannot answer the ask, so it stops instead of growing the chain.
- **Added: `/steer:work review` clears a PR review queue in one batch.**
  Draining a long queue was one PR at a time. `review` collects every PR
  awaiting your review in one call, sends draft, red and conflicting ones to
  *Blocked*, reviews the rest in parallel - one read-only subagent per PR,
  each returning a short card - and buckets them as *Ready*, *Changes*,
  *Look* or *Blocked*. You name the *Ready* PRs to approve and the approvals
  post in a single command, skipping any PR pushed to since its card was
  built. High-risk and drift-flagged PRs are never batch-approved, nothing is
  pre-selected, an unattended loop approves nothing, and it never merges.
  `review --mine` works the author's side of the same queue: it marks
  finished drafts ready, routes red ones to `resume`, retargets an
  independent stacked PR onto the default branch, and asks who should review
  an unassigned one.
- **Added: the steer status band is now clickable, with a detail pane.** Each count in the band above the prompt (features, open questions, ADRs to ratify, work claims) is a button that opens a `steer` pane listing the items behind it: features with their status, open questions ranked blocking-first with their `required_before`, Proposed ADRs, and claimed issues with their branch (or title, for older markers). Each row has a button that puts the owning command in the prompt (`/steer:spec <feature>`, `/steer:spec adr accept <n>`, `/steer:work resume #<n>`, ...) and closes the pane; nothing is sent until you press Enter, so every gate stays yours. A steer-fault count fills a plain-language ask to report it, which Claude routes to `/steer:report`. `scripts/workspace-snapshot.sh --items` is the new machine-readable source the pane reads; it runs only while the pane is open.
- **Changed: the bundled GitHub workflows run on `ubuntu-26.04` instead of `ubuntu-latest`.** GitHub moves `ubuntu-latest` to Ubuntu 26.04 between October 19 and November 19, 2026 and warns on every run until then. Naming the image explicitly silences the warning and means the next image change is a reviewed template bump, not a shift under running CI. Applies to `ci.yml`, `claude.yml`, `copilot-setup-steps.yml`, `dependabot-auto-merge.yml` and `steer-loop.yml`. actionlint does not know the new label yet, so the scaffold also ships `.github/actionlint.yaml` declaring it. `/steer:setup sync` carries existing repos over through a migration entry. A repo that depends on Ubuntu 24.04-specific packages can pin `ubuntu-24.04` instead.
